# Party Mode 讨论记录: 统一登录与双角色系统重构

**日期**: 2026-02-23
**参与者**: PM, UX Designer, Architect, Dev
**主题**: 关键决策讨论

---

## 📋 讨论摘要

### 核心共识

1. **一次性实现双角色系统**
   - 不分阶段,直接实现完整功能
   - 降低 UX 复杂度,避免多次改版

2. **并行开发策略**
   - Week 1: 数据库迁移 + 核心认证
   - Week 2-7: 前后端并行开发
   - 总时长: 7 周(2月底-4月中旬)

3. **技术可行性确认**
   - 数据库迁移风险可控
   - 手机验证码登录实现简单
   - 双角色系统架构清晰

4. **时间线确认**
   - 目标: 2026年9月新学期前完成
   - 实际开发: 2月底-4月中旬(7 周)
   - 预留缓冲: 4月中旬-8月底(测试 + 灰度)

---

## 🎯 关键决策

### 决策 1: 一次性实现双角色系统

**理由**:
- PM: 用户体验更流畅,避免多次改版
- UX: 符合"极简登录"愿景
- Architect: 技术上完全可行
- Dev: 工作量在可控范围内

**风险缓解**:
- 充分的测试覆盖
- 灰度环境先验证
- 保留回滚方案

### 决策 2: 并行开发策略

**Week 1: 后端优先**
- Architect: 数据库迁移脚本
- Dev: 核心 API(认证、用户管理)
- UX: 完成设计细节

**Week 2-7: 前后端并行**
- Dev: 后端 API + 前端页面
- Architect: 代码审查 + 技术支持
- UX: 组件规范 + 设计评审

### 决策 3: 7 周时间线

**Phase 1: Week 1-3** - 核心功能
- 统一登录
- 双角色系统
- 首登信息补全

**Phase 2: Week 4-5** - 教师工作台
- 批改页面
- AI 集成
- 学生历史

**Phase 3: Week 6-7** - 学生工作台 + 测试
- 作业提交
- 长期记忆库
- 集成测试

## ⚠️ 风险与缓解

### 风险 1: 数据库迁移失败

**概率**: 中
**影响**: 高
**缓解**:
- 在灰度环境先测试
- 准备回滚脚本
- 数据备份

### 风险 2: 教师批改页面复杂度超预期

**概率**: 中
**影响**: 中
**缓解**:
- Week 3 先实现基础版
- Week 4 逐步添加功能
- 预留缓冲时间

### 风险 3: AI 服务不稳定

**概率**: 低
**影响**: 中
**缓解**:
- 使用多个 AI 模型(降低单点故障)
- 实现 fallback 机制
- 缓存 AI 结果
